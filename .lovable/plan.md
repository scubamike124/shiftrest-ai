# Email Deliverability & Security — Investigation Findings

## Root Cause (Primary)

**Anchor/href domain mismatch on the "Verify Email" button.**

The auth webhook (`src/routes/lovable/email/auth/webhook.ts`) passes `payload.data.url` straight into the templates as `confirmationUrl`. That URL is generated by Supabase Auth and, unless explicitly customized, resolves to:

```
https://czsgjqfcjiuqirvmdlps.supabase.co/auth/v1/verify?token=...&redirect_to=https://restpilotai.com/...
```

So the visible button labeled "Verify Email" sits inside a message branded RestPilot AI, sent from `notify.restpilotai.com`, but the actual href points to `*.supabase.co`. Gmail's phishing heuristics flag exactly this pattern — branded sender + button whose link goes to an unrelated third-party domain — with the red "This message might be dangerous" banner. This is the same class of warning that first-time recipients on iOS Gmail hit before, and it is why tapping the button did nothing (Gmail disables links when it shows that banner).

## Contributing Factors

1. **From-name is a dev slug, not a brand.** `SITE_NAME = "shift-rest-ai"` in the webhook, so the header renders as `shift-rest-ai <noreply@notify.restpilotai.com>`. Gmail cross-checks display name vs brand of the domain; a slug that doesn't match "RestPilot AI" adds suspicion weight.
2. **No `Reply-To`.** The enqueue payload sets `from` but no `reply_to`. Support address `support@restpilotai.com` is never advertised to the MTA.
3. **`siteUrl` is `https://restpilotai.com`** — good — but it's unused for the actual verify action because Supabase controls that URL.
4. **Supabase Auth `Site URL` / `Additional Redirect URLs`** must include only `https://restpilotai.com` (and `https://www.restpilotai.com`). Any leftover preview/lovable/localhost entries let Supabase generate `redirect_to` values that Gmail treats as suspicious.

## What is NOT the problem

- **SPF/DKIM/DMARC/alignment.** `notify.restpilotai.com` is delegated to Lovable via NS records; Mailgun signs with aligned DKIM `d=notify.restpilotai.com` and SPF passes via the delegated zone. Domain reputation is neutral (fresh subdomain) but authenticated. The Gmail warning is *content-based*, not auth-based — auth-failure warnings read "Be careful with this message" and mention SPF/DKIM explicitly, which is not what you saw.
- **HTTPS.** All URLs in the template are HTTPS.
- **Token security.** Supabase tokens are single-use, expire (default 24 h for signup, 1 h for recovery), and are cryptographically random. No open-redirect risk in our code — `redirect_to` is constrained by the Auth allow-list.
- **Template markup.** No suspicious formatting, hidden text, or link cloaking. React Email escapes props; no `dangerouslySetInnerHTML`.

## Verdict on ownership

- **Not Gmail's fault** — the heuristic is correct given the current headers/body.
- **Not DNS or Lovable Emails/Mailgun** — auth is passing.
- **Ours to fix**, in three places: Supabase Auth config (Site URL + email template link), the webhook constants (From name, Reply-To), and confirmation-URL rewriting so the visible link points to `restpilotai.com`.

## Recommended Fix

**Strategy: route every auth link through `https://restpilotai.com` so href domain aligns with sender domain.**

1. **Add an auth callback route** at `src/routes/auth.callback.tsx` (or reuse `/auth`) that accepts `?token_hash=...&type=signup|recovery|...&next=/dashboard` and calls `supabase.auth.verifyOtp({ token_hash, type })` client-side. This lets us use Supabase's PKCE/OTP verify flow with a link on our own domain.
2. **In Supabase Auth email templates** (managed via the Lovable hook), swap Supabase's default `{{ .ConfirmationURL }}` for a rewritten URL built from `{{ .TokenHash }}` and `{{ .EmailAction }}`:
   `https://restpilotai.com/auth/callback?token_hash={{ .TokenHash }}&type={{ .EmailAction }}&next=/dashboard`
   The Lovable auth webhook already renders the template server-side, so we build this URL from `payload.data.token_hash` + `payload.data.email_action_type` in `webhook.ts` and pass it as `confirmationUrl` instead of `payload.data.url`.
3. **Fix webhook constants** in `src/routes/lovable/email/auth/webhook.ts`:
   - `SITE_NAME = "RestPilot AI"` (used for the friendly From name)
   - `from: 'RestPilot AI <noreply@notify.restpilotai.com>'`
   - Add `reply_to: 'support@restpilotai.com'` to the enqueue payload; the queue processor forwards it to Mailgun as the `h:Reply-To` header.
4. **Set Supabase Auth Site URL** to `https://restpilotai.com` and Additional Redirect URLs to only `https://restpilotai.com/**` and `https://www.restpilotai.com/**`. Remove any `*.lovable.app`, preview, or localhost entries.
5. **Optional hardening**: add `List-Unsubscribe` header for auth mail (Mailgun sets it automatically for transactional but explicit is better), and a plain-text alt-body for every template (already emitted by `render(element, { plainText: true })`).

## File-by-file Changes (when approved)

- `src/routes/lovable/email/auth/webhook.ts` — brand `SITE_NAME`, rewrite `confirmationUrl` to `https://restpilotai.com/auth/callback?...`, add `reply_to` to enqueue payload.
- `src/routes/auth.callback.tsx` — new route; calls `supabase.auth.verifyOtp` and redirects to `next`.
- `src/lib/email-templates/signup.tsx`, `recovery.tsx`, `magic-link.tsx`, `invite.tsx`, `email-change.tsx`, `reauthentication.tsx` — no code change (they already accept `confirmationUrl`); verify preview text and CTA copy read cleanly for Gmail's spam scoring.
- Supabase Auth settings (dashboard config, not a file) — Site URL + redirect allow-list.

## Verification Plan (post-fix)

1. **Header check** — send a real signup to a Gmail address, open "Show original":
   - `SPF=PASS`, `DKIM=PASS d=notify.restpilotai.com`, `DMARC=PASS`, `From: RestPilot AI <noreply@notify.restpilotai.com>`, `Reply-To: support@restpilotai.com`.
2. **Link check** — hover the "Verify Email" button; href must start with `https://restpilotai.com/auth/callback?...`. No `supabase.co`, no `lovable.app`, no `localhost`.
3. **No red banner in Gmail (web + iOS).** Send to a fresh Gmail account with no prior history; confirm the "dangerous" warning is gone.
4. **Click-through works end to end** — button opens `restpilotai.com/auth/callback`, session is created, redirect to `/dashboard`. Token cannot be reused (second click errors with "already verified" or "expired").
5. **`email_send_log`** row transitions `pending → sent` with correct `template_name`.
6. **Deliverability spot checks** — mail-tester.com score ≥ 9/10; Google Postmaster Tools shows domain reputation "Medium" or better after ~24 h of live traffic.
7. **Regression** — recovery, magic-link, invite, email-change flows all land on `restpilotai.com/auth/callback` and complete.

## Risk

Low. The verify-otp callback pattern is Supabase's documented flow for custom-domain auth links. Rollback is a one-line revert to `payload.data.url` if the callback route misbehaves.
